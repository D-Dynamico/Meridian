**Decisions**
- Only a UTM source is measured in place (D15). The old rule, "projected and in metres",
  would have measured Web Mercator directly at +22.3 percent area error.
- Missing `.prj` stores `EPSG:4326` with `crs_assumed: true` instead of null (D10 revised).
  The brief needs every feature to report a CRS; the flag is what carries the warning.
- Per-feature `source_crs` column, file `crs` becomes `MIXED` when layers disagree. A zip
  can hold several shapefiles with different `.prj` files.
- `make_valid` output is filtered to polygon parts. Nothing left means "degenerate
  polygon", never a length.
- Beyond 84°N or 80°S, UTM does not exist: the geodesic value is reported, with a note and
  a null `measurement_crs`.
- Notes joined with `"; "` in a fixed order (D16). Every result carries every field.
- Startup marks orphaned `PENDING` and `PROCESSING` files `FAILED` (D17).
- Hidden slashless route aliases (D18). The 307 problem was overstated in the review:
  httpx and requests both follow it and resend the body. Kept anyway to save a round trip.
- `feature_index` column (D19), for readability only. SQLModel quotes `index` fine.
- Stage 1 upload schedules no task. Files stay `PENDING` until the Stage 4 processor.
- Follow-up from the user's review: explicit `measurement_method` (`projected` or
  `geodesic`) on every measured feature, and `geodesic_value` is never null on a measured
  feature, including the polar fallback (D22). Consumers should not have to infer the
  method from a null `measurement_crs`.
- Settled: 50 MB upload limit (D20); 409 for measurements while `PENDING`, `PROCESSING` or
  `FAILED`, with the failure reason in `detail` (D21); Python 3.12 on `python:3.12-slim`
  (D23).

**Surprises**
- The planned 0.1 percent projected against geodesic tolerance would have failed a correct
  implementation. It only held because the Jaipur fixture sits 0.8° from its zone's central
  meridian. Measured area gaps: Jaipur -0.064%, central meridian at the equator -0.080%,
  Bengaluru +0.116%, zone edge at the equator +0.195%. Max length gap 0.098%. New
  tolerances: 0.25% area, 0.15% length.
- A 1 km square drawn in UTM coordinates measures exactly 1,000,000 m2 in that zone and
  tests nothing. Fixtures must be built with `Geod.fwd`.
- Hemisphere bugs do not show in areas: 56°N and 56°S squares measure identically. Tests
  must assert the EPSG code.
- `Geod.geometry_area_perimeter` returns negative area for clockwise rings, which is what
  every Shapefile exterior is.
- `make_valid` on a zero-area sliver returned a MultiLineString, which a naive dispatcher
  would have measured as a length.
- pyogrio warns (it is not silent) when a multi-layer KML is read without naming a layer.
  It is still easy to miss in a background task's log, so the convention stands.
- LIBKML adds about 11 mostly-null system columns to KML properties. Left as an open
  decision for Stage 2.
- Git on this machine converts LF to CRLF on checkout (`core.autocrlf`). Harmless for
  docs; consider a `.gitattributes` in Stage 1 so the Dockerfile and shell files stay LF.

- **The planned size check could not work where the docs put it.** FastAPI reads and
  parses the whole multipart body (`fastapi/routing.py`, `await request.form()`) before
  any dependency or handler runs, so a `Content-Length` check in the route fires only
  after a 2 GB upload has been fully received. Moved to ASGI middleware. It must raise
  `HTTPException`: FastAPI re-raises that from body parsing, but turns any other
  exception into a generic 400 "There was an error parsing the body".
- **Three tests that could not fail**, each found by mutation:
  - The `.gitattributes` test passed with the `*.shp` rule deleted, because Windows sets
    `core.ignorecase` and `*.SHP` matched instead. The test now forces it off to see
    what Linux sees.
  - Unwiring the size middleware left every test green: the route's own size check also
    returns 413. Middleware tests now upload an unsupported extension, so a 413 can only
    come from the middleware (the route would say 415).
  - The filename test used `C:\...\survey.kml`, but python-multipart already strips
    drive-letter paths before the route sees them, so the route's base-name step was
    never exercised. Relative and POSIX paths do arrive intact; the test uses those now.
- The ad hoc mutation script corrupted `app/api/files.py`: `read_text()` defaults to
  cp1252 on Windows, and writing back as UTF-8 double-encoded every `§`. Caught by a
  non-ASCII grep, repaired, script fixed to pass `encoding="utf-8"`. Any file tooling on
  this machine needs an explicit encoding.
- A UTC fix that was not needed. I added a validator to re-attach UTC to timestamps,
  assuming SQLite returns naive datetimes. The mutation check removing it stayed green:
  SQLModel 0.0.47 maps `datetime` fields to its own `UTCDateTime` type, which already
  returns aware UTC values. Validator removed. The test that the API says `...Z` stays,
  and forcing a plain SQLAlchemy `DateTime` column turns it red, so it guards against a
  SQLModel upgrade changing this.
- Starlette 1.7 deprecates `httpx` for its TestClient in favour of `httpx2`, a drop-in
  swap.
- The GitHub repo `D-Dynamico/Meridian` already existed and was **public** (anonymous API
  returned 200). The push was held until the user made it private (anonymous API then
  returned 404), then Stage 0 and Stage 1 were pushed together (`7d22006..31ffbb0`).
  It must be made public again at submission (`WORKFLOWS.md` §14).

- **Stage 2, probing real pyogrio 0.13 / GDAL 3.12.4 before writing the loader:**
  - "GDAL's KML reader returns Z = 0" was wrong. GDAL keeps what the file has; Google
    Earth exports write `,0`. The "note Z only when non-zero" rule stands, wording fixed.
  - LIBKML fills `tessellate` (-1), `extrude` (0) and `visibility` (-1) on every feature
    even when the file omits them. The planned "drop where null" would have kept them
    everywhere. Decided D26 on that evidence.
  - Nested KML folders come back as flat sibling layers. Duplicate folder names become
    `Plots (#2)`, unnamed folders `Layer2`.
  - A KML with no placemarks has zero layers, and GeoPandas' default read then crashes
    with a bare `IndexError`. The loader returns an empty file instead.
  - **GDAL reads a shapefile with no `.dbf` without complaint** and returns geometry with
    no attributes. The required-part check is the only thing enforcing the brief's
    "properties" requirement.
  - GDAL error messages quote the absolute server temp path. Scrubbed.
  - GDAL writes shapefile exteriors clockwise: confirmed, supporting the geodesic `abs()`.
- **The planned zip-bomb byte counting was dead code.** I wrote it, then checked: Python's
  zipfile never yields more than an entry's declared size, and a header that understates
  it fails the CRC check. Counting could never fire. Removed; the declared-size check is
  the guard (D25).
- **Two more tests that could not fail**, found by mutation:
  - Backslash zip-slip (`..\evil.shp`) on Windows: zipfile converts `\` to `/` in entry
    names on write and on read wherever `os.sep` is a backslash, so the loader's own
    replacement never ran here. On Linux it is the only thing that catches it. Now also
    tested on `_safe_members` directly, which is platform-independent.
  - A KML `set_crs(4326)` fallback that GDAL makes unreachable. Removed; a test pins
    GDAL's EPSG:4326.
  - One mutation of mine was itself wrong (`False and A or B` still runs `B`), which
    looked like a missed macOS-filter test until rerun as a plain `return False`.
- **`numpy.float64` is a subclass of `float`** (and `numpy.str_` of `str`). The first
  version of `to_json_safe` checked plain types first, so a numpy float passed through
  still a numpy scalar. Caught by the type assertion in the unit test; numpy checks now
  come first, and a mutation that swaps the order back is caught.
- Confirmed the user's finding on pandas 3.0.6: missing strings, numbers and dates all
  come back as float NaN, plain `json.dumps` writes them, and only
  `json.dumps(allow_nan=False)` (what Starlette uses) fails. Every serialization test
  therefore uses the strict form.
- **Stage 4: D29's premise was half wrong for this stack.** With `to_json_safe` removed,
  the measurements endpoint still returned 200 with nulls. NaN was stored as
  `{"area": NaN}` (invalid JSON; SQLite's `json_valid` returns 0), but Pydantic
  serializes NaN as null through a `response_model`, so the response hid it. Only a
  plain-dict route gives the expected 500 (probed: `/model` 200, `/plain` 500). So the
  real danger is silent invalid JSON in the database. The round-trip test now also
  checks the stored text with `json_valid`, and that alone goes red without the helper.
  D29, the helper's docstring and CLAUDE.md corrected.
- Stage 4: the summary test first checked total area against 1 km2 within 0.5 percent,
  which a mutation adding the 1000 m line to the area (1,001,000 m2) slipped through.
  Now compared exactly with the stored feature values.
- Stage 4: with the real processor wired in, five upload tests broke at once, because
  TestClient runs background tasks before returning and the upload was processed and
  deleted before the assertions. This is exactly the race D28's injection removes: the
  default test client now swaps in a recorder.
- Startup recovery assumes a single server process; with several workers one worker's
  startup would fail another's in-flight file. Recorded in D17.
- **Stage 3: `abs()` on the geodesic area is not enough** (it was the documented rule).
  It fixes only the overall sign. A MultiPolygon with one clockwise and one
  counter-clockwise part of equal size measured 0, and a hole wound like its exterior was
  added instead of subtracted (1,039,960 m2 instead of 959,961 m2). Rings are now oriented
  with `shapely.orient_polygons` first (D30), and `abs()` is gone because it would be
  dead code. A mutation that puts `abs()` back in place of orientation is caught.
- **A collinear polygon is valid in shapely**, so `make_valid` never runs on it. Its area
  in degrees was floating-point dust, not 0, and once transformed it measured 139 m2
  projected and 137 m2 geodesic, because a line straight in lon/lat is curved in UTM and
  on the ellipsoid. Now judged as "no area" by a unitless ratio in the source CRS
  (D31). An exact `== 0` mutation is caught.
- **The 0.25 percent cross-check band cannot tell a neighbouring zone from the right
  one.** The UTM scale-factor formula predicted every gap within 0.0022 percent
  (Jaipur -0.0646 vs -0.0647, Bengaluru +0.1161 vs +0.1147, zone edge +0.1944 vs
  +0.1922), so tests assert the gap against it within 0.005 percent.
- `force_2d` was dead code: shapely's area and length, `shapely.transform` and `Geod` are
  all 2D. Removed; a rising-line test now pins the behaviour instead.
- Bash heredocs keep mangling backslashes and quotes in embedded Python. Multi-line
  edits now go through a script file written with the editor.
