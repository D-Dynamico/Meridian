- Close-out: `CLAUDE.md` status, `ARCHITECTURE.md` §3 module map (adds `scripts/`), and

**Decisions**
- Samples are generated, not hand-drawn, and built on the ground with `Geod.fwd` like the
  accuracy fixtures, so the README can state their true areas. They are still committed,
  because a reviewer should not have to run a script before the first upload.
- Only the KML is compared byte for byte with its generator. The shapefile `.dbf` header
  records the date it was written, so the zip changes every day it is regenerated; its
  content is pinned by the end-to-end test instead. Zip entry timestamps are fixed for the
  same reason.
- The sample KML is indented. The test builders write one long line, which is fine for
  tests but not for a reviewer opening the file.
- The parcels zip uses UTM rather than EPSG:4326. Every KML is EPSG:4326, so a 4326
  shapefile would have shown the same path twice.
- One uvicorn process in the image, stated in a comment next to `CMD`. Several workers
  would break D17's startup recovery, and `BackgroundTasks` already gives concurrency
  through the threadpool.
- Tests ship in the image (one 689 MB image rather than a separate test stage). The
  geospatial wheels dominate the size either way, and running the suite inside the image
  is the only way this Windows machine exercises Linux-only paths such as the backslash
  zip-slip replacement.
- README examples are real responses captured from the Docker container, not the
  illustrative values in `API.md`. Every note and error string it quotes was checked
  against the code. The README links to `API.md` for the full reference instead of
  copying all of it, so only one place lists every error message.
- After review, the user asked why the README was so long (538 lines). Most of it
  repeated `docs/`: three full JSON responses with a field guide (most of `API.md`
  again), the processing flow told twice, and a paragraph per learning. Trimmed to 335:
  one example per endpoint linking to `API.md`, safety points instead of the numbered
  flow, one or two lines per learning. The CRS section and samples table stayed whole,
  because they are what a mapping reviewer reads first.
- Learnings are taken from the Stage 1 to 6 "Surprises" sections, keeping only those a
  reviewer can check or that changed a design decision.
- Non-root user. The code stays owned by root, so the app cannot modify itself; only
  `/data` is writable.

**Surprises**
- A mixed `MultiGeometry` (point plus line) arrives from GDAL as a `GeometryCollection`
  and gets the unsupported note; a `MultiGeometry` of two lines arrives as a
  `MultiLineString` and is measured. Probed before choosing the sample.
- The UTM-stored parcels report a projected area 0.116 percent above their ground area,
  exactly the scale-factor prediction for Bengaluru. Measuring in place does not remove
  UTM's distortion; it only skips a transform that would give the same numbers. The
  geodesic value is the closer answer to the ground.
- A "never measure UTM in place" mutation could not be caught by the parcels sample:
  UTM to EPSG:4326 and back to the same zone gives the same coordinates and the same
  area. The existing measure tests catch it by the code path; the sample test does not
  pretend to.
- **pytest could not run in the container as first written.** The non-root user cannot
  write `.pytest_cache` in the root-owned code folder; pytest only warns, but with
  `-W error` the warning failed the run after every test had passed. Fixed with
  `-p no:cacheprovider` in the documented command, rather than giving the user write
  access to the code.
- Docker was installed but its daemon was not running; Docker Desktop had to be started.
- Git Bash rewrites `/data` in `docker exec` arguments into `C:/Program Files/Git/data`.
  `MSYS_NO_PATHCONV=1` stops it. Worth a line in the README for Windows reviewers only if
  a documented command needs a container path; none does.
- The first Docker fresh-clone build failed with `failed to list workers ... EOF`: the
  Docker Desktop daemon dropped the BuildKit connection, minutes after it had been
  started. `docker info` and `buildx ls` were healthy a moment later and the identical
  rerun passed. Nothing in the repo changed between the two. My script also kept going
  after the failed build and produced a wall of connection errors that looked like an
  app failure; the rerun gated each step on the previous one.

## Security review and cleanup, before publishing

**Scope:** at the user's request, a security review of the whole codebase (the skills
only look at unpushed changes, and there were none) and a search for redundant code. The
user then asked for the layer caps and separate processing threads, the D8 and redundancy
cleanup, and for their personal email not to become public.

**Changes**
- D32: `load` takes `max_layers` (100 by default in `Settings`) and refuses more
  shapefiles in a zip or folders in a KML before reading any layer. Processing runs in
  its own pool of `Settings.processing_threads` (2) through `in_processing_threads` in
  `main.py`; `Processor` in `deps.py` may now be async. Tests in `test_loader.py`,
  `test_processor.py` and `test_app.py`; 7 mutations added, and the stale "real
  processor not wired" pattern updated. Docs: `DECISIONS.md` D32, `ARCHITECTURE.md` §5
  and §7, `API.md` §8.5, `TEST_PLAN.md` §16, README.
- This repo's `user.email` is set locally to the GitHub noreply address, so no new
  commit carries the personal one. The global git config is unchanged.

**Decisions**
- A cap rather than a timeout: a Python thread cannot be killed, so a timeout would only
  stop waiting for work that keeps running.
- 100 layers: generous for real survey files, which group features into a handful of
  folders, and small enough that the folder-squared term stays at about 2 s.
- A separate pool rather than making the routes async: the routes are plain `def` on
  purpose (D14), and the problem was the shared pool, not the routes.
- The limiter is created on first use, because anyio needs a running event loop to
  create one, and `create_app` runs before there is one.
- Reading a KML once instead of once per folder is left open. It is the real fix for
  large legitimate KMLs, but needs investigation into what pyogrio and LIBKML allow.

**Surprises**
- **The KML loader is quadratic in folder count.** 500 empty folders took 39 s and 1,000
  took 155 s. Each per-layer read appears to re-parse the whole document.
- **My first cost model was wrong, and the real-server check caught it.** I
  extrapolated per-byte cost and told the user a genuine 5 MB, 200-folder KML would
  take about 20 minutes. Four 2 MB files with 100 folders each finished within seconds,
  because the padding was one long text value. Measured properly: the cost grows with
  folders squared plus folders times features. At the cap, an 8.4 MB file with 100,000
  points takes 45 s against 2.3 s in one folder, so about 4.5 minutes at 50 MB.
- Background tasks shared Starlette's 40-thread pool with every `def` route, `/health`
  included. Confirmed in `starlette/background.py` and `concurrency.py`; not reproduced
  with 40 live uploads.
- LIBKML is safe against hostile XML on both platforms: a DTD with entities (file or
  URL, and the billion-laughs bomb) is refused with a parse error, and `NetworkLink`,
  external DTDs and remote style URLs are never fetched. Probed against a local HTTP
  server, which got no hits.
- `pip-audit` found no known vulnerabilities; no secrets or data files in git history.
  29 commits carry the user's personal email as author and committer.

**Verification**

  count ignored, no KML cap, KML cap off by one, no shapefile cap, shapefile cap off by
