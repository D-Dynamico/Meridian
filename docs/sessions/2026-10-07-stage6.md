# 2026-10-07 Stage 6: packaging and README

**Scope:** Stage 6 from `WORKFLOWS.md` §13: sample files, Dockerfile, README with every
section the brief requires, and a fresh-clone check with both venv and Docker, against
the definition of done in §14.

**Changes**
- `scripts/make_samples.py` writes `samples/survey.kml` and `samples/parcels.zip`, both
  committed. The KML (near Jaipur, three folders) holds a 1 km square, a self-intersecting
  plot, a 1 km road, a gate point and a mixed `MultiGeometry`, so one upload shows area,
  repair, length, a point and an unsupported type. The zip holds 1, 3 and 5 hectare
  parcels near Bengaluru stored in EPSG:32643 with a `.prj`, so the second upload takes
  the measure-in-place path that the KML cannot. `tests/test_samples.py` pins both, and
  `TEST_PLAN.md` §16 lists it.

**Decisions**
- Samples are generated, not hand-drawn, and built on the ground with `Geod.fwd` like the
  accuracy fixtures, so the README can state their true areas. They are still committed,
  because a reviewer should not have to run a script before the first upload.
- Only the KML is compared byte for byte with its generator. The shapefile `.dbf` header
  records the date it was written, so the zip changes every day it is regenerated; its
  content is pinned by the end-to-end test instead. Zip entry timestamps are fixed for the
  same reason.
- The sample KML is indented. The test builders write one long line, which is fine for
  tests but not for a reviewer opening the file.
- The parcels zip uses UTM rather than EPSG:4326. Every KML is EPSG:4326, so a 4326
  shapefile would have shown the same path twice.

**Surprises**
- A mixed `MultiGeometry` (point plus line) arrives from GDAL as a `GeometryCollection`
  and gets the unsupported note; a `MultiGeometry` of two lines arrives as a
  `MultiLineString` and is measured. Probed before choosing the sample.
- The UTM-stored parcels report a projected area 0.116 percent above their ground area,
  exactly the scale-factor prediction for Bengaluru. Measuring in place does not remove
  UTM's distortion; it only skips a transform that would give the same numbers. The
  geodesic value is the closer answer to the ground.
- A "never measure UTM in place" mutation could not be caught by the parcels sample:
  UTM to EPSG:4326 and back to the same zone gives the same coordinates and the same
  area. The existing measure tests catch it by the code path; the sample test does not
  pretend to.
